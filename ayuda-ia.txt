## 1. Entrada del programa

El flujo comienza en `main.cpp`:

```bash
./ircserv <port> <password>
```

El programa valida:

- Que existan exactamente dos argumentos.
- Que el puerto sea numérico.
- Que esté entre `1` y `65535`.
- Que la contraseña no esté vacía.

Después crea:

```cpp
Server server(port, argv[2]);
server.run();
```

Si ocurre una excepción, se muestra el error y el programa termina.

## 2. Arquitectura general

La implementación está dividida principalmente en cuatro clases:

| Clase | Responsabilidad |
|---|---|
| `Server` | Sockets, clientes, canales y bucle principal |
| `Client` | Estado y buffers de cada conexión |
| `Message` | Parseo de comandos IRC |
| `Channel` | Miembros, operadores, invitaciones y modos |
| `CommandHandler` | Ejecución de comandos IRC |

La relación principal es:

```text
Server
 ├── Client*
 ├── Channel*
 └── CommandHandler
       └── Server&
```

`CommandHandler` recibe una referencia al servidor para poder buscar clientes, canales y enviar respuestas.

---

## 3. Servidor y sockets

`Server::setupSocket()` configura el socket TCP:

1. Ignora `SIGPIPE` para evitar que `send()` termine el proceso.
2. Instala un handler para `SIGINT`.
3. Crea un socket IPv4/TCP.
4. Activa `SO_REUSEADDR`.
5. Configura el socket como no bloqueante.
6. Hace `bind()` sobre `INADDR_ANY`.
7. Ejecuta `listen()`.
8. Añade el socket de escucha a `_pollFds`.

El servidor utiliza:

```cpp
poll(&_pollFds[0], _pollFds.size(), -1);
```

Esto permite atender múltiples clientes sin crear un hilo por conexión.

---

## 4. Bucle principal

`Server::run()` espera eventos de `poll()`:

- `POLLIN` en el socket principal: llega un nuevo cliente.
- `POLLIN` en un cliente: hay datos disponibles.
- `POLLOUT`: hay respuestas pendientes por enviar.
- `POLLHUP`, `POLLERR` o `POLLNVAL`: la conexión debe cerrarse.

El flujo normal es:

```text
poll()
  ├── nueva conexión → acceptClient()
  ├── datos recibidos → handleClientData()
  ├── datos pendientes → send()
  └── error/desconexión → disconnectClient()
```

Cuando se pulsa `Ctrl+C`, `poll()` se interrumpe por `SIGINT`, el bucle termina y el destructor libera los recursos.

---

## 5. Gestión de clientes

Cada cliente se almacena en:

```cpp
std::map<int, Client *> _clients;
```

La clave es el descriptor del socket.

Un `Client` contiene:

- `_fd`: descriptor del socket.
- `_nickname`: nickname IRC.
- `_username`: username.
- `_realname`: nombre real.
- `_inputBuffer`: datos recibidos parcialmente.
- `_outputBuffer`: datos todavía no enviados.
- `_hasPassed`: si validó `PASS`.
- `_hasUserCommand`: si envió `USER`.
- `_registered`: si terminó el registro.
- `_disconnectRequested`: si pidió desconexión.

### Recepción de datos

`recv()` puede devolver:

```text
PASS secret\r\nNICK usuario\r\n
```

o solamente una parte:

```text
PASS sec
```

Por eso los datos se acumulan en `_inputBuffer`.

`Client::getNextLine()` busca `\n`, extrae una línea completa y elimina `\r` si existe. Esto permite procesar correctamente mensajes IRC terminados en:

```text
\r\n
```

También soporta varios comandos recibidos en un solo `recv()`.

## 6. Buffer de salida

Las respuestas no se envían directamente desde cada comando. Se agregan mediante:

```cpp
client.queueOutput(message);
```

Después `Server::updatePollEvents()` activa `POLLOUT`.

Cuando el socket está listo:

```cpp
send(fd, output.c_str(), output.size(), 0);
```

La cantidad enviada se elimina con:

```cpp
client.consumeOutput(sent);
```

Esto es importante porque `send()` puede enviar solamente una parte del mensaje.

## 7. Parseo de mensajes IRC

La clase `Message` separa una línea en:

- Prefijo opcional.
- Comando.
- Parámetros.

Por ejemplo:

```text
:nick!user@localhost PRIVMSG #general :Hola mundo
```

Se transforma aproximadamente en:

```text
prefix  = nick!user@localhost
command = PRIVMSG
params  = ["#general", "Hola mundo"]
```

El parser también normaliza el comando a mayúsculas:

```text
privmsg → PRIVMSG
join    → JOIN
nick    → NICK
```

Soporta el parámetro final IRC introducido por `:`:

```text
PRIVMSG #canal :mensaje con espacios
```

### Limitaciones del parser

Esta versión todavía tiene varias limitaciones:

- Solo trata el espacio `' '` como separador.
- No limita el número de parámetros según RFC.
- No valida estrictamente nombres, longitudes o caracteres IRC.
- Un prefijo sin comando se considera inválido.
- No genera respuestas numéricas para líneas mal formadas.

## 10. Canales

Los canales se almacenan en:

```cpp
std::map<std::string, Channel *> _channels;
```

Cada canal contiene:

- Nombre.
- Topic.
- Contraseña.
- Miembros.
- Operadores.
- Invitaciones.
- Modo invite-only.
- Modo topic restringido.
- Límite de usuarios.
- Clave del canal.

Los miembros se identifican mediante su descriptor de socket:

```cpp
std::set<int> _members;
```

Esto permite comprobar:

```cpp
channel->hasMember(fd);
channel->isOperator(fd);
channel->isInvited(fd);
```

Al eliminar un miembro también se eliminan sus privilegios de operador y sus invitaciones:

```cpp
void Channel::removeMember(int fd)
{
    _members.erase(fd);
    _operators.erase(fd);
    _invited.erase(fd);
}
```

Cuando un canal queda vacío, `Server::removeChannelIfEmpty()` lo elimina de memoria.

## 11. Desconexión

Cuando un cliente ejecuta `QUIT`, se desconecta o produce un error:

1. Se notifica `QUIT` a los miembros de sus canales.
2. Se elimina de cada canal.
3. Se eliminan los canales vacíos.
4. Se destruye el objeto `Client`.
5. Se elimina su descriptor de `_pollFds`.
6. Se cierra el socket.

El mensaje enviado a los demás usuarios tiene esta forma:

```text
:nick!user@localhost QUIT :reason\r\n
```

La gestión de memoria utiliza punteros crudos, pero el destructor de `Server` intenta liberar todos los `Client*` y `Channel*`.

Por tanto, esta versión parece ser una **estructura parcialmente migrada o incompleta**. El diseño ya separa los comandos por categorías, pero los archivos correspondientes no fueron incluidos o no
están en la rama publicada.

Consecuencia probable:

```text
make
```

fallaría primero porque no encuentra los archivos de `src/commands/`, y aun eliminando esas referencias aparecerían errores de linker por métodos sin definición.

## 13. Otros puntos pendientes

El archivo `notas.txt` indica tareas todavía abiertas:

```text
seguir protocolo RFC1459
normalizar los nombres de los canales
probarlo con HexChat, testeando con valgrind los leaks de memoria y las señales
```

Esto coincide con el estado del código:

- No hay normalización de nombres de canales.
- No se observa validación completa conforme a RFC 1459.
- Faltan implementaciones de comandos.
- No hay tests automatizados.
- `README.md` está vacío.
- `_signalPipe` está declarado, pero no se utiliza.
- La gestión de errores de `recv()` podría distinguir mejor `EAGAIN` y `EWOULDBLOCK`.
- Solo se acepta una conexión por evento de `poll()`, en vez de aceptar hasta vaciar la cola.
- La estructura usa raw pointers en lugar de una gestión de propiedad más segura.

## Resumen

La versión tiene una buena base conceptual:

```text
socket no bloqueante
        ↓
poll()
        ↓
Client con buffers
        ↓
Message parser
        ↓
CommandHandler
        ↓
Channel / Server state
```

Pero no es todavía una implementación funcional completa de `ft_irc`. La parte de red, buffers, parser, estados y estructura de canales está iniciada; la lógica IRC real y los archivos de comandos
parecen faltar en esta versión publicada.
